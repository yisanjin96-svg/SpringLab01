## 2026-10-08 JPQL / API 명세서
- 배운 것 : JPQL(`@Query`)로 조회 쿼리를 직접 쓰는 규칙, API 명세서 쓰는 방법을 배웠다
- 구현한 것 : 클린 아키텍처 23장(데이터베이스 게이트웨이)이 들어간 `AirportRepository` 조회 쿼리를 구현했다
- 피드백 : 쿼리 옆에 "이 줄이 뭘 하는지" 주석을 직접 단 건 좋음. 외우지 말고 이렇게 계속 설명해 보기.

## 2026-10-09 공항 전체 조회 / service · dto · controller
- 배운 것 : DTO는 `final` + 생성자 + getter로 만드는 규칙, 엔티티 → DTO 변환은 service에서 하는 규칙, `ResponseEntity`로 응답하는 방법을 배웠다
- 구현한 것 : 클린 아키텍처 20장(유스케이스)이 들어간 `AirportService`, 22장(경계를 넘는 데이터)이 들어간 `AirportResponse`, 22장(인터페이스 어댑터)이 들어간 `AirportController`를 구현했다
- 피드백 : 흐름은 잘 이어졌는데, 메서드 이름을 `findAllAirportId`처럼 실제로 돌려주는 것과 다르게 지었음. 이름은 "이게 진짜 뭘 돌려주나"를 보고 짓기.

## 2026-10-09 항공편 조회 / domain · repository
- 배운 것 : 엔티티에 실제 테이블 컬럼을 연결하는 방법, 다른 도메인(공항)은 객체가 아니라 코드(ID)로만 들고 있는 규칙을 배웠다
- 구현한 것 : 클린 아키텍처 20장(엔티티)이 들어간 `Flight`, 23장(데이터베이스 게이트웨이)이 들어간 `FlightRepository.searchFlights`를 구현했다
- 피드백 : 쿼리에 `departure_at`(DB 이름)을 써서 틀렸음. 쿼리 쓸 때 "지금 보는 게 DB 테이블인지 자바 클래스인지" 먼저 확인하는 습관 필요.

## 2026-10-11 지적받은 부분 수정
- 배운 것 : JPQL은 컬럼 이름이 아니라 엔티티 필드 이름을 쓴다, Repository의 ID 타입은 엔티티 `@Id` 타입과 맞춰야 한다는 걸 배웠다
- 구현한 것 : `FlightRepository` ID 타입 `Long`으로 수정, `findAllAirports`로 이름 복구 (직접 수정)
- 피드백 : 지적받은 걸 바로 직접 고친 건 좋음. 다만 커밋을 여러 파일 한 번에 몰아서 함. 정해 둔 규칙(파일 단위 커밋)부터 지키기.

## 2026-10-11 항공편 조회 / dto
- 배운 것 : 응답 DTO에는 화면에 필요한 값만 넣는 규칙, getter 1개가 JSON 항목 1개가 되고 `@RestController`가 그걸 자동으로 바꿔 준다는 것, 엔티티는 DB 쪽 모양이고 DTO는 프론트 쪽 모양이라 나눠 둔다는 걸 배웠다
- 구현한 것 : 클린 아키텍처 22장(경계를 넘는 데이터)이 들어간 `FlightResponse`를 구현했다 (AI가 작성)
- 피드백 : 공항 DTO랑 똑같은 패턴인데 직접 안 치고 맡겼음. 다음 service는 꼭 먼저 직접 쳐 보기.

## 2026-10-11 항공편 조회 / service
- 배운 것 : 메서드를 부를 때는 `( )`에 인자를 넣고 `;`로 끝내야 한다, 파일 이름과 `public class` 이름은 대소문자까지 같아야 한다, 현재 일시는 service에서 만들어 넘긴다는 걸 배웠다
- 구현한 것 : 클린 아키텍처 20장(유스케이스)이 들어간 `FlightService.searchFlights`를 구현했다 (직접 시작 → 막혀서 AI가 완성)
- 피드백 : 공항 service를 옆에 두고 똑같이 따라 하면 됐는데, 메서드에 값을 받는 칸(매개변수)을 안 만들고 부르려 했음. "이 메서드는 뭘 받아서 뭘 돌려주나"를 먼저 정하고 치기.

## 2026-10-11 항공편 조회 / controller (입력값 검사 전)
- 배운 것 : `@RequestParam`으로 주소 뒤 `?키=값`을 받는 방법, `@GetMapping("path")`처럼 글자를 넣으면 주소 뒤에 그대로 붙는다는 걸 배웠다
- 구현한 것 : 클린 아키텍처 22장(인터페이스 어댑터)이 들어간 `FlightController.searchFlights`를 구현했다 (직접 작성)
- 피드백 : 공항 controller를 보고 혼자 끝까지 쳤음, 좋음. 다만 자동완성이 넣어 준 `"path"`를 그대로 둘 뻔했음. 자동완성 결과는 한 번 읽고 넘어가기.

## 2026-10-11 항공편 조회 / 실행 확인
- 배운 것 : Docker로 DB를 띄우고, 앱을 실행하면 엔티티 기준으로 테이블이 자동 생성된다는 것, SQL로 먼저 확인한 결과와 API 결과가 같아야 한다는 걸 배웠다
- 구현한 것 : X1(`GET /api/flights`)과 X0(`GET /api/airports`) 응답 확인 완료. 이미 출발한 편(JL300)은 빠지는 것까지 확인
- 피드백 : DB가 비어 있으면 "할 게 없다"가 아니라 테스트 데이터부터 넣고 보는 것. 확인할 데이터를 직접 만드는 것도 개발의 일부.
