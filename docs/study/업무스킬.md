## 1. 일괄 갱신 (一括更新)

### 어디서 쓰이는가

- 명세 화면에서 여러 행의 수량・단가를 고치고 "저장" 버튼을 한 번 누를 때
- 특정 주문에 속한 명세 전체의 단가를 같은 값으로 바꿀 때

### 왜 필요한가

화면은 여러 행의 데이터를 한 번의 요청으로 보냅니다.
서버는 그 여러 행을 한 번의 처리 안에서 전부 DB에 반영해야 합니다.

### 동작 원리

일괄 갱신에는 목적이 다른 두 가지 방식이 있습니다.

| 방식 | 발행되는 SQL | 적합한 상황 |
|---|---|---|
| A. 엔티티를 하나씩 수정 | 행마다 UPDATE 1회 | 행마다 바꿀 값이 다를 때 |
| B. UPDATE 문 1회 | 조건에 맞는 행 전체에 UPDATE 1회 | 모든 행을 같은 값으로 바꿀 때 |

**방식 A의 핵심 원리: 변경 감지 (変更検知 / ダーティチェック)**

JPA는 DB에서 엔티티를 조회할 때, 그 시점의 값을 복사본 (スナップショット)으로 따로 보관합니다.
트랜잭션이 끝나는 순간, JPA는 현재 엔티티의 값과 복사본을 비교합니다.
값이 달라진 엔티티가 있으면, JPA가 그 엔티티에 대한 UPDATE 문을 자동으로 발행합니다.
그래서 방식 A에서는 `save()`를 호출하지 않아도 DB가 갱신됩니다.

### 구현 — 방식 A

```java
@Service
public class OrderService {

    private final OrderDetailRepository detailRepository;

    public OrderService(OrderDetailRepository detailRepository) {
        this.detailRepository = detailRepository;
    }

    @Transactional
    public void updateDetails(List<OrderDetailForm> forms) {
        // 1. 更新対象のIDを集める
        List<Long> ids = forms.stream()
                .map(OrderDetailForm::getId)
                .toList();

        // 2. 1回のSELECTでまとめて取得し、IDで引けるMapにする
        Map<Long, OrderDetail> detailMap = detailRepository.findAllById(ids).stream()
                .collect(Collectors.toMap(OrderDetail::getId, d -> d));

        // 3. 画面の値をエンティティに反映する
        for (OrderDetailForm form : forms) {
            OrderDetail detail = detailMap.get(form.getId());
            if (detail == null) {
                throw new IllegalArgumentException("明細が存在しません: id=" + form.getId());
            }
            detail.setQuantity(form.getQuantity());
            detail.setPrice(form.getPrice());
        }

        // 4. save()は不要。トランザクション終了時に変更検知でUPDATEが発行される
    }
}
```

**2번에서 한 번에 조회하는 이유**

루프 안에서 `findById()`를 행마다 호출하면, SELECT가 행 개수만큼 실행됩니다.
명세가 100행이면 SELECT도 100번 실행됩니다.
`findAllById()`로 한 번에 조회하면 SELECT는 `WHERE id IN (...)` 1번으로 끝납니다.

**`@Transactional`을 붙이는 이유**

`@Transactional`이 없으면, 3행째에서 에러가 났을 때 1・2행째만 갱신된 어중간한 상태가 DB에 남습니다.
`@Transactional`이 있으면, 에러가 났을 때 그 처리 안의 모든 갱신이 취소 (ロールバック)됩니다.

### 구현 — 방식 B

```java
public interface OrderDetailRepository extends JpaRepository<OrderDetail, Long> {

    // 注文に属する明細すべての単価を、1回のUPDATEで変更する
    @Modifying
    @Query("UPDATE OrderDetail d SET d.price = :price WHERE d.orderId = :orderId")
    int updatePriceByOrderId(@Param("orderId") Long orderId, @Param("price") Integer price);
}
```

방식 B는 엔티티를 조회하지 않고 DB에 직접 UPDATE 문을 보냅니다.
그래서 방식 B는 변경 감지를 거치지 않습니다.

### 왜 이 방법인가 / 다른 방법은 없는가

| 질문 | 답 |
|---|---|
| 기초 패턴인가 | 네. 업무 시스템에서 가장 자주 쓰는 패턴입니다. |
| 이 방법밖에 없는가 | 아닙니다. 행마다 값이 다르면 A, 전부 같은 값이면 B를 고릅니다. |
| 주의할 점 | 대량 INSERT에서는 `saveAll()`을 써도 기본 설정으로는 INSERT가 1행씩 실행됩니다. `hibernate.jdbc.batch_size` 설정이 필요하고, ID 생성 방식이 `IDENTITY`이면 그 설정도 효과가 없습니다. |

## 2. 차분 갱신 (差分更新)

### 어디서 쓰이는가

- 명세 편집 화면에서 사용자가 행을 추가하고, 일부 행을 수정하고, 일부 행을 삭제한 뒤 한 번에 저장할 때
- 실무에서 "명세 갱신"이라고 하면 대부분 이 패턴입니다.

### 왜 필요한가

화면은 "무엇을 추가했고 무엇을 삭제했는지"를 보내지 않습니다.
화면은 편집이 끝난 "최종 상태의 목록"만 보냅니다.
그래서 서버가 DB의 현재 목록과 화면의 목록을 비교해서, 추가・수정・삭제를 스스로 판단해야 합니다.

### 동작 원리

판단 규칙은 3가지입니다.

| 화면의 행 | DB의 행 | 처리 |
|---|---|---|
| id가 없음 | — | 새로 추가된 행 → INSERT |
| id가 있음 | 같은 id가 있음 | 기존 행 → UPDATE |
| — | 화면 목록에 없는 id | 사용자가 지운 행 → DELETE |

### 구현

```java
@Transactional
public void syncDetails(Long orderId, List<OrderDetailForm> forms) {
    // 1. DBにある現在の明細を取得し、IDで引けるMapにする
    List<OrderDetail> currentDetails = detailRepository.findByOrderId(orderId);
    Map<Long, OrderDetail> currentMap = currentDetails.stream()
            .collect(Collectors.toMap(OrderDetail::getId, d -> d));

    // 画面から届いた既存明細のIDを記録する
    Set<Long> receivedIds = new HashSet<>();

    for (OrderDetailForm form : forms) {
        if (form.getId() == null) {
            // 2. IDなし → 新規追加
            OrderDetail newDetail = new OrderDetail();
            newDetail.setOrderId(orderId);
            newDetail.setItemName(form.getItemName());
            newDetail.setQuantity(form.getQuantity());
            newDetail.setPrice(form.getPrice());
            detailRepository.save(newDetail);
        } else {
            // 3. IDあり → 既存明細の更新
            OrderDetail detail = currentMap.get(form.getId());
            if (detail == null) {
                // この注文に属さないIDが送られてきた場合は不正とみなす
                throw new IllegalArgumentException("不正な明細IDです: id=" + form.getId());
            }
            detail.setItemName(form.getItemName());
            detail.setQuantity(form.getQuantity());
            detail.setPrice(form.getPrice());
            receivedIds.add(detail.getId());
        }
    }

    // 4. DBにあるが画面に無い明細 → 削除
    List<OrderDetail> toDelete = currentDetails.stream()
            .filter(d -> !receivedIds.contains(d.getId()))
            .toList();
    detailRepository.deleteAll(toDelete);
}
```

**3번에서 `currentMap`으로 확인하는 이유**

`currentMap`은 "이 주문에 속한 명세"만 들어 있는 Map입니다.
악의적인 사용자가 다른 주문의 명세 id를 보내면, 그 id는 `currentMap`에 없습니다.
그래서 이 확인은 다른 사람의 데이터를 수정하는 공격을 막는 역할도 합니다.

### 왜 이 방법인가 / 다른 방법은 없는가

다른 방법으로 "전체 삭제 후 재등록 (全削除・全登録)"이 있습니다.
전체 삭제 후 재등록은 그 주문의 명세를 전부 DELETE하고, 화면의 목록을 전부 INSERT하는 방법입니다.

| 비교 항목 | 차분 갱신 | 전체 삭제 후 재등록 |
|---|---|---|
| 코드의 단순함 | 복잡함 | 매우 단순함 |
| 명세 id | 유지됨 | 저장할 때마다 바뀜 |
| 다른 테이블이 명세 id를 참조할 때 | 문제 없음 | 참조가 깨짐 |
| 작성일・작성자 같은 이력 | 유지됨 | 사라짐 |

| 질문 | 답 |
|---|---|
| 기초 패턴인가 | 네. 명세가 있는 화면이면 거의 반드시 나옵니다. |
| 이 방법밖에 없는가 | 아닙니다. 명세 id를 아무도 참조하지 않고 이력도 필요 없으면, 전체 삭제 후 재등록도 실무에서 쓰입니다. 기존 프로젝트가 어느 쪽을 쓰는지 먼저 확인해야 합니다. |

## 3. 동적 검색 (動的検索)

### 어디서 쓰이는가

- 검색 화면에 "고객명・상태・기간" 입력란이 있고, 사용자가 입력한 항목만 조건으로 쓰고 싶을 때

### 왜 필요한가

사용자가 무엇을 입력할지는 실행 전에는 알 수 없습니다.
고객명만 입력할 수도 있고, 아무것도 입력하지 않을 수도 있습니다.
그래서 입력된 값에 따라 WHERE 조건을 실행 시점에 조립해야 합니다.

### 동작 원리

입력값이 비어 있으면 그 조건을 빼고, 값이 있으면 그 조건을 AND로 붙입니다.

```
고객명="山田", 상태=빈칸  →  WHERE customer_name LIKE '%山田%'
고객명=빈칸, 상태="APPLIED" →  WHERE status = 'APPLIED'
둘 다 빈칸               →  WHERE 없음 (전체 조회)
```

**문자열 연결로 SQL을 만들면 안 되는 이유**

`"WHERE name = '" + input + "'"`처럼 입력값을 SQL 문자열에 직접 붙이면, 입력값 안의 `'`가 SQL 문법으로 해석됩니다.
공격자는 이것을 이용해 의도하지 않은 SQL을 실행시킬 수 있고, 이 공격을 SQL 인젝션 (SQLインジェクション)이라고 부릅니다.
JPA의 조건 조립 기능은 입력값을 SQL 문법이 아니라 "값"으로만 DB에 전달하므로 이 공격이 통하지 않습니다.

### 구현 (JPA Specification)

```java
public interface OrderRepository
        extends JpaRepository<Order, Long>, JpaSpecificationExecutor<Order> {
}
```

```java
public class OrderSpecs {

    // 顧客名の部分一致。未入力ならnullを返し、条件から外す
    public static Specification<Order> customerNameContains(String name) {
        return (root, query, cb) ->
                (name == null || name.isBlank())
                        ? null
                        : cb.like(root.get("customerName"), "%" + name + "%");
    }

    // 状態の完全一致
    public static Specification<Order> statusEquals(OrderStatus status) {
        return (root, query, cb) ->
                status == null ? null : cb.equal(root.get("status"), status);
    }

    // 作成日の期間指定(開始日以降)
    public static Specification<Order> createdFrom(LocalDateTime from) {
        return (root, query, cb) ->
                from == null ? null : cb.greaterThanOrEqualTo(root.get("createdAt"), from);
    }
}
```

```java
public List<Order> search(OrderSearchCondition cond) {
    // nullを返した条件は自動的に無視される
    Specification<Order> spec = Specification
            .where(OrderSpecs.customerNameContains(cond.getCustomerName()))
            .and(OrderSpecs.statusEquals(cond.getStatus()))
            .and(OrderSpecs.createdFrom(cond.getCreatedFrom()));

    return orderRepository.findAll(spec);
}
```

### 왜 이 방법인가 / 다른 방법은 없는가

| 질문 | 답 |
|---|---|
| 기초 패턴인가 | 네. 검색 화면이 있으면 반드시 나옵니다. |
| 이 방법밖에 없는가 | 아닙니다. 일본 SI 현장에서는 MyBatis의 `<if>` 태그로 SQL 안에서 조건을 분기하는 방식도 많이 쓰입니다. 그 밖에 QueryDSL이라는 라이브러리도 있습니다. 원리는 모두 "입력값이 있을 때만 조건을 붙인다"로 같습니다. |
| 주의할 점 | `LIKE '%山田%'`처럼 앞에 `%`가 붙으면, DB는 인덱스를 쓸 수 없어서 전체 행을 하나씩 확인합니다. 데이터가 많은 테이블에서는 앞부분 일치 (`'山田%'`)로 바꿀 수 있는지 검토합니다. |

## 4. 페이지네이션 (ページネーション)

### 어디서 쓰이는가

- 목록 화면에서 "1페이지 20건"처럼 나눠서 보여줄 때

### 왜 필요한가

데이터가 10만 건일 때 전부 조회하면, 서버 메모리와 통신량이 크게 늘어나고 화면도 느려집니다.
사용자가 실제로 보는 것은 한 화면 분량뿐이므로, 그 분량만 DB에서 가져오면 됩니다.

### 동작 원리

페이지네이션은 SQL 2개로 이루어집니다.

```sql
-- ① 表示する分だけ取得(3ページ目、1ページ20件)
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 40;

-- ② 全件数を取得(「全○件・全○ページ」の表示用)
SELECT COUNT(*) FROM orders;
```

- `LIMIT 20`은 "20건만 가져온다"는 뜻입니다.
- `OFFSET 40`은 "앞의 40건을 건너뛴다"는 뜻입니다.
- `ORDER BY`가 반드시 필요합니다. 정렬 기준이 없으면, DB는 실행할 때마다 다른 순서로 행을 돌려줄 수 있습니다. 그러면 같은 행이 두 페이지에 나오거나 어떤 행이 누락됩니다.

### 구현

```java
public Page<Order> searchPage(OrderSearchCondition cond, int page) {
    Specification<Order> spec = Specification
            .where(OrderSpecs.customerNameContains(cond.getCustomerName()))
            .and(OrderSpecs.statusEquals(cond.getStatus()));

    // ページ番号は0始まり。作成日の降順で並べる
    Pageable pageable = PageRequest.of(page, 20, Sort.by("createdAt").descending());

    // 上記①と②のSQLがSpringによって自動で発行される
    return orderRepository.findAll(spec, pageable);
}
```

반환되는 `Page` 객체는 다음 값을 가집니다.

| 메서드 | 값 |
|---|---|
| `getContent()` | 이번 페이지의 데이터 목록 |
| `getTotalElements()` | 전체 건수 |
| `getTotalPages()` | 전체 페이지 수 |

### 왜 이 방법인가 / 다른 방법은 없는가

| 질문 | 답 |
|---|---|
| 기초 패턴인가 | 네. 목록 화면의 표준입니다. |
| 이 방법밖에 없는가 | 아닙니다. OFFSET 방식은 뒤쪽 페이지일수록 느려집니다. `OFFSET 100000`이면 DB가 10만 건을 읽고 버리기 때문입니다. 그래서 무한 스크롤이나 대량 데이터에서는 "마지막으로 본 행의 값보다 뒤"를 조건으로 가져오는 키셋 페이지네이션 (キーセットページネーション)을 씁니다. 업무 시스템의 일반 목록 화면에서는 OFFSET 방식이 대부분입니다. |

## 5. 입력 검증 (バリデーション)

### 어디서 쓰이는가

- 모든 등록・갱신 처리

### 왜 필요한가

화면 쪽 JavaScript 검증은 사용자가 브라우저 개발자 도구로 끄거나, 화면을 거치지 않고 직접 요청을 보내면 우회됩니다.
그래서 서버 쪽 검증이 반드시 필요하고, 화면 쪽 검증은 사용자 편의를 위한 보조 역할입니다.

### 동작 원리

일본 SI 현장에서는 검증을 3단계로 나눠서 부릅니다.

| 단계 | 의미 | 예 | 구현 위치 |
|---|---|---|---|
| 단항목 체크 (単項目チェック) | 항목 하나만 보고 판단 | 필수 입력, 최대 길이, 숫자 범위 | Form 클래스의 어노테이션 |
| 상관 체크 (相関チェック) | 여러 항목을 함께 보고 판단 | 시작일 ≤ 종료일 | Form 클래스의 메서드 |
| 업무 체크 (業務チェック) | DB를 조회해야 판단 가능 | 같은 이름의 주문이 이미 있는가 | Service 클래스 |

### 구현 — 단항목 체크와 상관 체크

## 6. 논리 삭제 (論理削除)

### 어디서 쓰이는가

- 고객・상품 같은 마스터 데이터 (マスタデータ)를 삭제할 때
- 주문처럼 나중에 "누가 언제 지웠는지" 확인해야 하는 데이터를 삭제할 때

### 왜 필요한가

실제로 행을 지우는 물리 삭제 (物理削除)를 하면, 데이터가 DB에서 완전히 사라집니다.
그러면 과거 주문이 참조하던 상품 정보가 사라지거나, 잘못 지웠을 때 복구할 수 없게 됩니다.

### 동작 원리

1. 테이블에 `deleted_at` 컬럼을 둡니다.
2. 삭제할 때 DELETE 대신 `UPDATE ... SET deleted_at = 현재시각`을 실행합니다.
3. 모든 조회에 `WHERE deleted_at IS NULL` 조건을 붙여서, 삭제 표시가 된 행을 보이지 않게 합니다.

3번을 조회마다 손으로 쓰면 반드시 누군가 빠뜨리므로, 프레임워크가 자동으로 붙이게 합니다.

### 구현

```java
@Entity
@Table(name = "orders")
// delete()が呼ばれたとき、DELETEの代わりにこのUPDATEを実行する
@SQLDelete(sql = "UPDATE orders SET deleted_at = CURRENT_TIMESTAMP WHERE id = ? AND version = ?")
// このエンティティへの全てのSELECTに、この条件を自動で付ける
@SQLRestriction("deleted_at IS NULL")
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String customerName;

    @Enumerated(EnumType.STRING)
    private OrderStatus status;

    @Version
    private Long version;

    private LocalDateTime createdAt;
    private LocalDateTime deletedAt;

    // getter / setter は省略
}
```

`@SQLDelete`의 SQL에 `version = ?`이 있는 이유는, 엔티티에 `@Version`(7장)이 있으면 Hibernate가 id와 version을 함께 넘기기 때문입니다.

이제 `orderRepository.delete(order)`를 호출하면, 실제로는 UPDATE가 실행됩니다.
`@SQLRestriction`은 Hibernate 6.3 이후의 이름이고, 그 이전 버전에서는 `@Where`라는 이름입니다.

### 왜 이 방법인가 / 다른 방법은 없는가

| 질문 | 답 |
|---|---|
| 기초 패턴인가 | 네. 일본 SI의 업무 시스템에서는 특히 많이 쓰입니다. |
| 이 방법밖에 없는가 | 아닙니다. 물리 삭제를 하면서, 지우기 직전의 데이터를 이력 테이블 (履歴テーブル)에 복사해 두는 방법도 있습니다. |
| 주의할 점 ① | 직접 쓴 네이티브 SQL (`nativeQuery = true`)에는 `@SQLRestriction`이 적용되지 않습니다. 직접 `deleted_at IS NULL`을 써야 합니다. |
| 주의할 점 ② | 메일 주소 같은 컬럼에 유니크 제약 (ユニーク制約)이 있으면, 삭제된 행도 남아 있으므로 같은 값으로 재등록할 수 없습니다. |
| 주의할 점 ③ | 삭제된 행이 계속 쌓이므로, 데이터가 많은 테이블에서는 조회 성능을 고려해야 합니다. |

## 7. 상태 관리 (ステータス管理)

### 어디서 쓰이는가

- 신청 → 승인 → 완료 같은 워크플로 (ワークフロー)
- 주문 → 출하 → 배송 완료 같은 진행 상태

### 왜 필요한가

상태는 정해진 순서로만 바뀌어야 합니다.
예를 들어, 이미 승인된 주문이 다시 "작성 중"으로 돌아가면 업무 규칙이 깨집니다.
그래서 "어떤 상태에서 어떤 상태로 갈 수 있는가"라는 규칙을 코드로 강제해야 합니다.

### 동작 원리

허용되는 상태 변화를 표로 정의하고, 이 표를 상태 전이 (状態遷移)라고 부릅니다.

| 현재 상태 | 이동 가능한 상태 |
|---|---|
| DRAFT (작성 중) | APPLIED |
| APPLIED (신청 중) | APPROVED, REJECTED |
| REJECTED (반려) | APPLIED |
| APPROVED (승인) | 없음 |

상태를 바꾸기 전에 항상 이 표를 확인하고, 표에 없는 이동이면 에러로 처리합니다.

### 구현

```java
public enum OrderStatus {
    DRAFT, APPLIED, APPROVED, REJECTED;

    // 状態遷移表:現在の状態から次の状態へ移れるかを判定する
    public boolean canTransitTo(OrderStatus next) {
        return switch (this) {
            case DRAFT -> next == APPLIED;
            case APPLIED -> next == APPROVED || next == REJECTED;
            case REJECTED -> next == APPLIED;
            case APPROVED -> false;
        };
    }
}
```

```java
public class Order {
    // フィールドは6章と同じ

    // 状態変更は必ずこのメソッドを通す
    public void changeStatus(OrderStatus next) {
        if (!this.status.canTransitTo(next)) {
            throw new BusinessException(this.status + " から " + next + " へは変更できません");
        }
        this.status = next;
    }
}
```

```java
@Transactional
public void approve(Long orderId) {
    Order order = orderRepository.findById(orderId)
            .orElseThrow(() -> new BusinessException("注文が存在しません"));
    order.changeStatus(OrderStatus.APPROVED);
    // 変更検知によりUPDATEが発行される(1章)
}
```

**`EnumType.STRING`을 쓰는 이유**

`EnumType.ORDINAL`(기본값)은 enum의 순서 번호 (0, 1, 2...)를 DB에 저장합니다.
나중에 enum 중간에 새 상태를 추가하면 번호가 밀려서, DB에 저장된 기존 데이터의 의미가 바뀌어 버립니다.
`EnumType.STRING`은 `"APPROVED"` 같은 이름을 저장하므로 이 문제가 생기지 않습니다.

**`@Version`을 쓰는 이유 — 낙관적 잠금 (楽観ロック)**

두 사람이 같은 주문을 동시에 열고, 한 사람은 승인하고 다른 사람은 반려하는 상황을 생각합니다.
`@Version`이 있으면, JPA는 UPDATE할 때 `WHERE id = ? AND version = (조회했을 때의 값)` 조건을 붙이고 version을 1 올립니다.
나중에 저장한 사람의 UPDATE는 version이 이미 바뀌었으므로 0행이 갱신되고, JPA가 예외를 던집니다.
그래서 먼저 저장한 사람의 결과를 나중 사람이 모르고 덮어쓰는 일이 막힙니다.

### 왜 이 방법인가 / 다른 방법은 없는가

| 질문 | 답 |
|---|---|
| 기초 패턴인가 | 네. 신청・승인이 있는 업무 시스템에서는 반드시 나옵니다. |
| 이 방법밖에 없는가 | 아닙니다. Service에 if 문으로 상태를 확인해도 동작합니다. 다만 그 경우 상태를 바꾸는 Service가 여러 곳이면 같은 확인을 여러 곳에 써야 하고, 한 곳만 빠뜨려도 규칙이 깨집니다. 엔티티와 enum에 규칙을 두면, 상태를 바꾸는 입구가 하나로 정해집니다. 상태가 매우 복잡하면 Spring Statemachine 같은 전용 라이브러리를 쓰기도 합니다. |

## 8. CSV 입출력 (CSVインポート・エクスポート)

### 어디서 쓰이는가

- 목록 화면의 "CSV 다운로드" 버튼
- 엑셀로 만든 데이터를 시스템에 한꺼번에 등록할 때

### 왜 필요한가

업무 담당자는 데이터를 엑셀로 집계하거나 수정하는 경우가 많습니다.
CSV는 엑셀과 시스템이 데이터를 주고받는 가장 일반적인 형식입니다.

### 동작 원리

**출력 (エクスポート)**

1. DB에서 데이터를 조회합니다.
2. 한 행씩 쉼표로 구분된 문자열로 만들어 응답에 씁니다.
3. 응답 헤더로 "이것은 다운로드할 파일이다"라고 브라우저에 알립니다.

**입력 (インポート)**

1. 업로드된 파일을 한 행씩 읽습니다.
2. 각 행을 검증하고, 에러가 있으면 행 번호와 함께 기록합니다.
3. 에러가 하나라도 있으면 아무것도 등록하지 않고, 에러 목록을 돌려줍니다.
4. 에러가 없으면 전부 등록합니다.

**직접 `split(",")`으로 처리하면 안 되는 이유**

값 안에 쉼표나 줄바꿈이 들어 있으면, CSV는 그 값을 `"山田, 太郎"`처럼 큰따옴표로 감쌉니다.
`split(",")`은 이 규칙을 모르므로 값을 잘못 나눕니다. 그래서 CSV 라이브러리를 씁니다.

**문자 코드 문제**

일본 엑셀은 BOM (バイトオーダーマーク)이 없는 UTF-8 파일을 열면 일본어가 깨집니다.
BOM은 파일 맨 앞에 붙이는 3바이트의 표시로, 엑셀은 이 표시를 보고 "UTF-8 파일이다"라고 판단합니다.
그래서 출력할 때 파일 맨 앞에 BOM을 씁니다. 프로젝트에 따라서는 Shift_JIS로 출력하는 경우도 있으므로, 기존 사양을 먼저 확인합니다.

### 구현 — 출력

```java
@GetMapping("/orders/csv")
public void exportCsv(HttpServletResponse response) throws IOException {
    response.setContentType("text/csv; charset=UTF-8");
    response.setHeader("Content-Disposition", "attachment; filename=\"orders.csv\"");

    Writer writer = new OutputStreamWriter(response.getOutputStream(), StandardCharsets.UTF_8);
    // Excelで文字化けしないよう、先頭にBOMを書き込む
    writer.write('\uFEFF');

    CSVFormat format = CSVFormat.DEFAULT.builder()
            .setHeader("ID", "顧客名", "状態", "作成日時")
            .build();

    try (CSVPrinter printer = new CSVPrinter(writer, format)) {
        for (Order order : orderRepository.findAll()) {
            printer.printRecord(
                    order.getId(),
                    order.getCustomerName(),
                    order.getStatus(),
                    order.getCreatedAt());
        }
    }
}
```

`findAll()`은 전체 데이터를 한 번에 메모리에 올립니다. 수십만 건 이상이면 메모리가 부족해지므로, 그때는 청크 처리 (チャンク処理)로 나눠서 읽습니다.

### 구현 — 입력

```java
@Transactional
public List<String> importDetails(Long orderId, MultipartFile file) throws IOException {
    List<String> errors = new ArrayList<>();
    List<OrderDetail> toSave = new ArrayList<>();

    CSVFormat format = CSVFormat.DEFAULT.builder()
            .setHeader()                // 1行目をヘッダーとして読む
            .setSkipHeaderRecord(true)  // ヘッダー行はデータとして扱わない
            .build();

    try (Reader reader = new InputStreamReader(file.getInputStream(), StandardCharsets.UTF_8);
         CSVParser parser = format.parse(reader)) {

        int lineNo = 1; // ヘッダー行を1行目として数える
        for (CSVRecord record : parser) {
            lineNo++;

            String itemName = record.get("商品名");
            if (itemName == null || itemName.isBlank()) {
                errors.add(lineNo + "行目:商品名は必須です");
                continue;
            }

            int quantity;
            try {
                quantity = Integer.parseInt(record.get("数量"));
            } catch (NumberFormatException e) {
                errors.add(lineNo + "行目:数量は数値で入力してください");
                continue;
            }

            OrderDetail detail = new OrderDetail();
            detail.setOrderId(orderId);
            detail.setItemName(itemName);
            detail.setQuantity(quantity);
            detail.setPrice(Integer.parseInt(record.get("単価")));
            toSave.add(detail);
        }
    }

    // 1件でもエラーがあれば、何も登録せずにエラー一覧を返す
    if (!errors.isEmpty()) {
        return errors;
    }

    detailRepository.saveAll(toSave);
    return errors;
}
```

엑셀에서 저장한 CSV에는 맨 앞에 BOM이 붙어 있는 경우가 있습니다.
BOM이 붙어 있으면 첫 번째 헤더 이름이 `"\uFEFF商品名"`으로 읽혀서, `record.get("商品名")`이 실패합니다.
이 경우 commons-io의 `BOMInputStream`으로 파일을 감싸서 BOM을 제거한 뒤 읽습니다.

### 왜 이 방법인가 / 다른 방법은 없는가

| 질문 | 답 |
|---|---|
